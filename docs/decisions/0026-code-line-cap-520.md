# 0026 代码文件行数上限提到 520 行，500 行停手

- 状态：已采纳（修订 0024 中「代码 300 / 400 行不变」一条）
- 日期：2026-11-01

## 背景

0024 把 Markdown 的行数上限抬到 520 行时，明确写了一句「代码文件 300 / 400 行均不变——代码按职责拆模块，行数与可读性的关系不同于文档」。理由是代码不该靠放宽阈值来逃避拆分。

维持一年多后，这条理由在实践里出现了两个问题：

1. **两套行数口径没有好处，只有记忆负担。** 维护时要同时记住 Markdown 520 / 32 KB、代码 400 行两套数，而 `doc_check.py` 里 `MD_LINE_MAX` 与 `CODE_LINE_MAX` 并列出现，读代码的人第一反应是「为什么不一样」。
2. **400 行在真实的工具文件上已经不敷使用。** `tools/deck_lint.py` 396 行，离上限只剩 4 行，读 PDF 坐标、判四类缺陷、出报告、做命令行全在一个文件里，功能上并没有该拆的第二个职责。再压下去只能拆出无人调用的私有函数，属于按字数机械切——正是 0005 明确禁止的做法。

同时维护者提出一条新约束：**触及 500 行就要停**，不是撞到上限才处理。

## 决定

代码文件建议上限 300 行 → **500 行**，硬上限 400 行 → **520 行**。与 Markdown 的硬上限对齐。

新增一条停手线，与阈值同处 `AGENTS.md`：**触及 500 行即停手，新增逻辑先拆模块**，不靠「还剩 20 行」续命。`doc_check.py` 对 500–520 行区间打印 `[提示]`，但不判缺陷。

单个函数 50 / 80 行、单个二级章节 60 / 100 行**不变**——函数与章节的规模与文件规模是两回事，这两个阈值判定的是「这段能不能一口气读完」，与仓库阈值无关。

## 理由

- **代码行数增长是单调的，文档不是。** 文档可以靠修订压缩，一行表格改写出三行短句再合回去是常事；代码加进去的函数不会自己消失。所以代码真正需要的是一条「别再写了」的线，而不是一个「还能写多少」的余量。500 行停手线就是这个角色，520 行硬上限只作为检查器的兜底。
- **上限对齐减少一处特殊规则。** Markdown 与代码同为 520 行，`doc_check.py` 的两个常量可以并排读，不用再解释「代码为什么更严」。
- **建议线取 500 而不是按 0024 的 67% 比例推（348）**：比例法适合文档，因为文档的建议线作用是「只允许修订」；代码的建议线如果定在 348，几乎每个工具文件都会立刻过线，那条线就退化成噪声。这里取整百数是有意的例外——0024 说过「整百数容易变成心理目标」，但代码的危险方向相反：目标不是「写满 500」，而是「见到 500 就别加」。数字凑整反而让这条线更容易在提交前被记起来。
- **不设 520 行以上的例外。** 硬上限没有例外，这条从 0005 起没变过。超过 520 行的代码文件先拆分再交付，不讨论「这次先留着」。

## 后果

- `tools/doc_check.py`：`CODE_LINE_MAX` 改为 `520`，新增 `CODE_LINE_WARN = 500` 与 `check_code_warn()`，文件头说明同步。500–520 区间输出 `[提示]`，退出码不受影响。
- `AGENTS.md` 阈值表「代码文件」一行改为 500 / 520，并在阈值表后补一段说明停手线与硬上限的分工。
- `tools/README.md` 的逐文件行数上限列按新口径重写：`deck_lint.py` 250 → 520，其余按实际职责重估，不再出现「声明 210、实际 228」这种自相矛盾的条目。
- `tools/mcp_tools.py` 与 `tools/smoke_rules.py` 里「越过 400 行上限」「守住 300 行上限」的历史注释改为指向本记录，保留「当时为什么拆」的信息，但不留失效的数字。
- `tools/smoke_rules.py`（228 行）与 `tools/build_flat.py`（206 行）此前超出各自声明预算，属声明值与实际脱节，随本次统一按 520 口径重新声明，不再单独记欠账。
- 0024 中「代码文件 300 / 400 行均不变」一条由本记录取代；0024 关于 Markdown 520 / 32 KB 与「禁止注水」的判断继续有效。
