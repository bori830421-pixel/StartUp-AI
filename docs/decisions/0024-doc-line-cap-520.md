# 0024 文档行数上限提到 520 行，同时禁止凑数

- 状态：已采纳（修订 0005 的行数项、0017 的建议线）
- 日期：2026-10-31

## 背景

合伙分支落地后 `SKILL.md` 到 265 行，越过 200 行建议线。按 0005 的规定，过线只能修订、新增内容必须另开文件；而这次要加的东西只有一行摘要。想加就得先做一次拆分手术，拆出来的往往只有十几行，索引成本反而上升。

这与 0017 复盘的是同一个病：**阈值从「防止文件过大」退化成「逼人频繁拆分」**。0017 当时抬的是体积（24 → 32 KB），行数没动；现在挡路的是行数。

同时要防另一头：上限抬高后，容易出现「反正还有两百行，多写点」的填充。用户明确提出这一条，作为本次改动的前提。

## 决定

Markdown 建议上限 200 行 / 16 KB → **350 行 / 22 KB**；硬上限 300 行 / 32 KB → **520 行 / 32 KB**。体积硬上限不动。

新增一条反向约束，与阈值同处 `AGENTS.md`：**上限是拆分触发器，不是写作目标。** 接近上限不是继续加内容的许可，而是回头看的信号；判断只看职责不看余量，新增内容让文件多出一个本该独立的职责就另开文件，哪怕还剩两百行。并列出注水的四种形态：同一件事换三种说法、一条判断拆成三条、补谁都不用的背景、表格改写成段落凑长度。

代码文件 300 / 400 行、单个函数 50 / 80 行、单个二级章节 60 / 100 行**均不变**——代码按职责拆模块，行数与可读性的关系不同于文档。

## 理由

- **行数放宽、体积不变，等于要求每行更短。** 32 KB / 520 行 ≈ 63 字节每行，原来的 32 KB / 300 行 ≈ 109 字节每行。这次放宽的是「能写多少条短判断」，不是「能装多少内容」——真正的字数上限一字节没动。这也正好贴合本项目「表格 + 短句」的文风。
- 建议线按原比例推：200 / 300 ≈ 67%，350 / 520 ≈ 67%；体积建议线同理 32 × 67% ≈ 22 KB。比例不变，阈值的含义就不变。
- 520 而不是 500：整百数容易变成心理目标，非整值能减少「凑到五百」的暗示。
- 只放宽行数不放宽体积，是因为体积才是载体的真实约束（0017、0019）。硬上限若跟着涨，等于用抬高阈值掩盖结构问题——这正是 0017 结尾警告过的事。

## 后果

- `tools/doc_check.py` 的 `MD_LINE_MAX` 改为 `520`，文件头说明同步。
- `AGENTS.md` 阈值表、自检说明、`docs/architecture-map.md`、`docs/verification-guide.md` 检查表四处文案同步。
- **`SKILL.md` 受 0019 载荷预算二次约束**：它被 B 单文件形态完整收录，体积涨到 32 KB 会让 flat 载荷约 27k token、32k 宿主占用升到八成以上。所以 `SKILL.md` 另守一条 28 KB 自律线；越过它要重算载荷预算，不是继续放宽。
- 0023 里「`SKILL.md` 必须拆分」从硬阻塞降为待办：现在 265 行仍有 55 行余量，但按新条款，判断依据回到职责而不是余量——「必须遵守」整节迟早要外移，理由不变，只是不再被行数逼着做。
- 0005 的行数项（200 / 300）与 0017 的建议线（200 行 / 16 KB）由本记录取代；0005 关于「拆分的依据是主题不是字数」的判断继续有效，本次改动正是执行它。
