# 决策记录 0005：文件规模与导航索引

- 状态：已采纳
- 日期：2026-10-28

## 背景

项目规则、决策记录、行为样例、行业档案都在持续追加。此前没有文件规模约束，也没有目录级索引，只有 `AGENTS.md` 一份逐条罗列的入口清单。

这种结构在文件少的时候没问题，文件多了会出三种故障：

1. **读取成本压过内容价值。** 一个规则文件涨到几千行后，智能体每次任务都要整篇加载，真正相关的几段被挤在大量无关内容里，判断质量下降。
2. **改动牵动全篇。** 只想加一条规则，却要在万行文件里定位插入点，冲突和误改概率随体量上升。
3. **找不到东西。** 没有目录索引时，只能靠文件名猜内容，或全文搜索；新增的文件也不会自动出现在入口清单里。

根因是把「一个文件」当成「一个仓库」用。

## 决定

1. **设定双阈值：** Markdown 建议上限 200 行 / 16 KB，硬上限 300 行 / 24 KB；代码 300 / 400 行；单函数 50 / 80 行；单个二级章节 60 / 100 行。行数与体积双卡，任一超标即算超标。
2. **过建议线只允许修订，过硬上限必须先拆再交付。** 硬上限不设例外。
3. **建立三级导航：** 一级是 `AGENTS.md` 的「项目文档入口」，只列到目录；二级是每个目录的 `README.md`，含职责、文件清单表、新增约定；三级是超过 120 行的文件顶部的「本文导航」锚点列表。
4. **一主题一文件。** 禁止垃圾桶文件；一次性记录（决策、样例、档案卡）新建编号文件，不追加到既有文件末尾。
5. **索引是导航契约。** 缺二级索引的目录、索引未登记的文件、索引里失效的链接，都算结构缺陷。
6. **拆分按主题切，不按字数截断。** 拆完必须同步上层索引，不留孤立文件。

## 理由

**为什么阈值定在 200 / 300 行：** 当前最大文件是 207 行的行业档案卡，其余多在 40–160 行。200 行是「一次能完整读完并保持结构感」的量级，300 行是「再大就必须拆」的底线。定得更低会逼出大量碎文件，反而增加索引负担。

**为什么同时卡行数和体积：** 行数管结构复杂度，体积管读取成本。表格密集的档案卡可能行数不多但字节很大，只卡行数会漏掉这类文件。

**为什么一级入口只列到目录：** 入口清单本身会随文件数线性膨胀，最终变成第二个万行文件。目录索引承担明细，入口只负责指路。

**为什么二级索引必须手写而不是自动生成：** 自动生成的清单只有文件名，没有「这个文件负责什么、现在什么状态」。对智能体来说，一句用途描述比一串路径有用得多。

**为什么不允许垃圾桶文件：** `其他.md` 一旦存在，所有不好归类的内容都会流进去，几个月后就是那个万行文件。找不到归属时新建主题文件，是唯一能长期维持的结构。

## 后果

- `AGENTS.md` 新增「文件规模与导航约束」一节，含阈值表、三级索引表、写作约束与交付前自检命令；「文档维护」增加一条「先看目录 `README.md` 确认主题归属」。
- `AGENTS.md` 与 `SKILL.md` 的入口清单都改为只列目录索引，原先逐条罗列的 18 个文件链接下沉到各目录 `README.md`。`SKILL.md` 原清单只列到决策记录 0002，0003 与 0004 已漏登记，是入口清单自然腐化的现成例证。
- 新增三个目录索引：`docs/README.md`、`references/README.md`、`data/README.md`。`examples/README.md` 与 `data/industries/README.md` 原已存在，继续沿用。
- 一次性为 8 个超过 120 行的存量文件补齐「本文导航」：`SKILL.md`、`references/checkup-scorecard.md`、`examples/11`、`12`、`13`、`data/industries/01`、`02`、`03`。
- `data/industries/03-shelf-ecommerce.md` 补导航后 229 行，已过建议线，进入「只修订不追加」状态；后续该卡内容增长时按「结构依据 / 实测清单 / 失败模式」拆卡，并在 `data/industries/README.md` 登记拆分关系。
- `SKILL.md` 的「阶段一：启动条件体检」单节 87 行，超建议线未过硬上限，结构靠三级标题维持；后续再增步骤时先拆成独立文件。
- `docs/verification-guide.md` 新增「文档结构检查」一节，把四项结构检查纳入交付验收。
- 后续所有新增文档沿用本规则；与本规则冲突的旧习惯以本记录为准。
