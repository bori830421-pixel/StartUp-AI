# 0017 文档硬上限从 24 KB 提到 32 KB

- 状态：已采纳（修订 0005 的体积一项）
- 日期：2026-10-30

## 背景

2026-10-30 给 `docs/verification-guide.md` 补一条退化形态时发现，该文件 24,355 字节，距 24 KB（24,576 字节）硬上限只剩 221 字节。加一行表格即超标，`doc_check.py` 退出码 1。当时按 0005 的「过硬上限先拆分」，把「闸门的关键检查点」整节抽成独立文件，降到 23.6 KB。

复盘时看到的问题不在这一次：24 KB 定于 0005 时，最大的文档约 12 KB，阈值留了一倍余量。此后文档普遍变长，`verification-guide.md`、`checkup-scorecard.md`、`runtime-loop.md` 都在 20 KB 以上，任何一次正常修订都要先做一次拆分手术。阈值从「防止文件过大」退化成了「逼人频繁拆分」，而拆出来的往往只有十几行，导航成本反而上升。

## 决定

Markdown 硬上限从 300 行 / 24 KB 改为 300 行 / 32 KB。建议上限维持 200 行 / 16 KB，行数上限维持 300 行。

同步改四处：`AGENTS.md` 的阈值表与自检说明、`docs/architecture-map.md` 的边界段、`docs/verification-guide.md` 的检查表、`tools/doc_check.py` 的常量与提示文案。提示文案改为读 `MD_BYTE_MAX`，不再硬编码数字。

## 理由

- 建议线与硬上限之间留 16 KB 缓冲，常见修订不必动结构；过建议线仍触发「只允许修订」。
- 单个二级章节 60 / 100 行、单函数 50 / 80 行的阈值不变，仍按 0005 执行——真正该拆的是结构，不是字数。
- 拆分的依据回到「一个文件一个主题」，不再由「再加一行就红」来驱动。

## 后果

- `doc_check.py` 的 `MD_BYTE_MAX` 改为 `32 * 1024`，报错文案读常量。
- 0005 的其余阈值继续有效，本次只改体积一项。
- 再遇到「只剩几百字节」时，先问是不是主题该拆，而不是再抬阈值。抬阈值解决的是余量，不是结构。
