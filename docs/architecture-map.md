# 架构地图

## 当前状态

项目处于规则与文档框架阶段，已有 24 个行为样例（`examples/`），以及 `tools/` 下的一套版式引擎与两个分发脚本。引擎只做排版：吃 JSON 出 pptx，不承担任何判断，因此不影响主流程的纯文档性质。除该引擎外没有实现代码、数据存储、外部集成或自动化任务；下列模块是技能的逻辑边界，不代表已有独立程序。

仓库不是安装单元：`dist/startup-guide/` 由 `tools/build_skill.py` 生成，是唯一可被宿主安装的形态（决策记录 0013）。

## 产品目的与使用者

本技能服务于创业新手，尤其是预算有限、方向尚不明确，或不知道自己该从哪一步开始的个人。

主流程是两阶段串行，中间有闸门：

```text
用户输入
  → 引导盘点 → 目的分离 → 待评估方向
  → 行业定位：落到国标门类，取原型候选
  → 资金带筛选：按预算排除不可能的原型
  → 识别原型：落到七种生意结构之一
  → 模式分叉：先确定用哪套成本结构算分
  → 定向检索：按原型生成检索计划，预算 = 线上必查项 × 2，上限 12
  → 七维体检：H1–H3 硬门槛、S1–S4 软约束
  → 闸门
      ├─ 放行 ────────→ 分阶段陪跑 P1→P2→P3→P4 → 阶段复盘
      ├─ 有条件放行 ──→ 补短板 → 复核 → 通过才进 P1
      ├─ 信息不足 ────→ 补测动作 → 回到对应门槛重判
      └─ 不建议启动 ──→ 最小代价出口 → 结束
```

闸门是这套架构的核心。它不是流程中的一个可选步骤，而是决定后续是否发生的判定点：没有通过体检，不产生阶段任务、预算表和行动计划。

闸门有四种去向，不是两种。只画「通过 / 不通过」会把「有条件放行」和「信息不足」压掉，而这两种恰恰是最常见的输入形态。

模式分叉位置在体检之前。同一类目下不同经营模式的成本结构完全不同，不分模式直接算钱，分数算得再细前提也是错的。规则见 `references/pattern-fork.md`。

定向检索位置在模式分叉之后、体检之前：结构来自原型，当前事实来自检索，参数来自用户实测。三者不能混用——用卡片回答事实问题，技能就退化成一个会过期的知识库。规则见 `references/runtime-loop.md` 与 `references/search-playbook.md`。

## 知识分层与更新

项目不以「预装所有行业知识」为目标，而采用按需取用、审慎沉淀的知识生命周期：

| 层 | 内容 | 使用与维护方式 |
| --- | --- | --- |
| 通用核心 | 体检闸门、原型判断、检索协议、证据标准、陪跑结构 | 随技能分发，跨行业复用；保持轻量，不塞入具体行业的全量操作资料 |
| 运行时资料 | 当前平台规则、地区政策、价格、供应与市场信号 | 按用户选定的项目和阶段检索；记录来源与日期，不能用旧卡片替代 |
| 业务模块 | 经复用验证的行业、平台或任务流程，例如小红书选品、找货源、上架与履约 | 根据用户当前项目和所处步骤按需加载；只有明确适用边界、来源和复核日期后才固化，过期后回到检索 |
| 候选经验 | 实际执行或阶段复盘中出现的观察、结果和解释 | 先区分事实、用户自述、推断与未知；审核通过前不作为规则或通用结论 |

知识沉淀遵循「候选经验 → 核实来源与适用范围 → 维护者审核 → 更新模块或样例 → 回归检查 → 版本发布」。成功或失败的单个案例不能直接推出因果或成功率；需要记录观察条件、时间范围、证据等级和仍未知的部分。项目不会因一次对话而自行改写判断规则。

任务型陪跑按一个可完成的经营动作推进，而不是一次倾倒整套行业知识。每一步应说明前置条件、要查的当前资料、具体操作、预期交付物、检查标准和停止条件；需要登录商家后台或做真实经营动作时，由用户操作并反馈结果，智能体据此指导下一步。示例：先确认目标客户与选品假设，再核实平台规则和供货条件，随后完成上架准备；每一步的判断都要回到来源或用户实测，不编造后台数据和经营结果。

本框架只定义知识的分层、审核与发布边界，不定义用户案例如何集中收集，也不引入公网服务器、后台或自动同步。当前没有跨用户自动学习能力；后续若要增加，需另行决策数据来源、授权与系统边界。

## 能力模块

| 模块 | 负责内容 | 主要输出 |
| --- | --- | --- |
| 引导盘点 | 用 8 道选择题收集目标、地区、能力、时间、资金和承受能力 | 盘点结果表 |
| 目的分离 | 区分用户要的是现金流、时间自由、做成自己的事还是学一门生意 | 评估口径说明 |
| 方向探索 | 从兴趣、技能或关键词提出可比较的创业假设 | 候选方向及适配理由 |
| 行业定位 | 把方向落到国标 20 门类之一，取原型候选，并给出 H3 的检索起点 | 门类、可及度、原型候选 |
| 资金带筛选 | 按预算落到六档之一，排除该档碰不了的原型；带位决定加载哪些原型卡 | 带位与该档的致命约束 |
| 原型识别 | 把方向落到七种生意结构之一，识别叠加原型 | 原型定位与结构推演 |
| 模式分叉 | 同一类目下先确定用哪套经营模式的成本结构算分，默认取最轻的模式 | 模式结构对比与重算后的分项 |
| 运行时检索 | 按原型生成检索计划并执行，预算按必查项算（×2，上限 12），校验来源后分级 | 检索计划、检索记录表 |
| 离线降级 | 检索跑不起来时先告知再降级：判定五类「搜不了」，工具缺凭据时先走公开端点兜底，端点全失败才降级并带检索记录，结论封顶在信息不足 | 降级提示、检索清单、带空缺的判断 |
| 启动条件体检 | 三个硬门槛加四个软约束，用用户信息、原型结构与检索到的当前事实 | 体检报告与分项依据 |
| 信息不足处理 | 区分「没测过」与「测了不够」，把未测项挂起，其余维度照常算 | 补测动作与分岔结论 |
| 行业档案引用 | 把档案卡当检索缓存，按数据级别与复核日期决定能否进入判断 | 结构依据与实测清单 |
| 闸门判定 | 输出放行、有条件放行、信息不足或不建议启动 | 一句判断与短板清单 |
| 下一步唯一动作 | 不管结论落在哪一档，每轮输出以一个当天能开始、做完能做决定的动作结尾 | 单个动作与判断标准 |
| 分阶段陪跑 | 一次交付一个阶段：目标、动作、交付物、话术、账本、判断点 | 阶段任务包 |
| 交付边界与加项管理 | 收钱前写死范围与加项价目，加需求逐项报价，砍价换减项不换价格 | 需求确认单、变更确认、结算单 |
| 阶段复盘 | 三选一并区分执行、假设、方向三类原因；硬门槛已不过时先补门槛再重跑 | 复盘记录 |
| 交付整理 | 将经用户审阅的方案组织为报告、演示文稿或 PDF 内容；页序与每页结论句先定，写不出结论句的页砍掉 | 文档大纲、页面文案 |
| 演示文稿渲染 | 按 brief 渲染 16:9 文件，跑遮挡/重叠自检；缺依赖时降级为可粘贴文案 | pptx 文件或逐页文案 |

## 数据与集成边界

- 用户输入是个性化建议的主要依据；未获用户提供或未核实的信息应标成假设或待验证。
- 本阶段不定义持久化用户数据，不收集不必要的个人或商业敏感信息。
- 市场、法规、价格、平台政策等动态事实需要按任务使用可用的联网来源核实，并记录来源与访问日期。
- 检索有预算：线上必查项 × 2，上限 12 个查询。预算用完无论是否查全都出结论，空缺项标为空缺并转成用户的实测动作。线下必查项不占预算。
- 联网能力是外部依赖，不保证可用。不可用时先告知再降级：结论封顶在「信息不足」，不允许把卡片内容当作检索结果。规则见 `references/offline-degradation.md`。
- 静态卡片（`data/archetypes/`、`data/industries/`）只决定搜什么、怎么判，不提供结论。行业卡是检索缓存，超过六个月只当检索起点，超过十二个月视为无卡。
- 行业、平台和任务知识按需维护，不追求预先覆盖全部行业；新增模块必须有明确复用价值、来源与复核日期。运行产生的经验先进入候选状态，审核和样例回归通过前不得作为通用规则。
- PPT/PDF 文件生成分三级（`references/deck-spec.md` 第 6 节）：`tools/deck_engine.py` 可运行就出文件；缺 python-pptx 交可粘贴文案；连排版都不做时只给页序。降级前先告知。引擎依赖 python-pptx 与系统中文字体，属可选加速器，不是主流程前置条件。
- 当前不包含后台任务、自动监控、外部账号写入或自动发布。

## 入口与文件边界

- `SKILL.md` 是 AI 使用入口，保持为流程与规则索引。
- `INSTALL.md` 是接入入口：三种宿主形态、验证动作、失败处理。
- `README.md` 是对外说明，供第一次接触本项目的人快速了解范围与用法。
- `AGENTS.md` 是项目协作与维护规则。它只对维护者生效，正文不得要求使用者读它。
- `docs/` 保存架构、能力与验证说明及决策记录。
- `references/` 保存可复用的提问、评分与陪跑模板；未来的任务型操作指南按用户问题拆分，避免把单个平台的全套流程塞进核心入口。
- `examples/` 保存行为样例，每个样例对应 `docs/verification-guide.md` 中的一个验收场景，用于证明规则可执行。
- `data/` 保存数据分级规则与检索缓存。原型卡按生意结构组织，决定搜什么、怎么判；行业卡是已检索结果的缓存，每张标注数据级别、来源与复核日期，过期只当检索起点。行业、平台或具体任务材料都按需维护，不要求一次装入全量资料。
- `hosts/` 保存分宿主接入页：目录技能、MCP、纯文本三形态各自的落点与坑。它进安装单元，因为装完之后换形态时仍要用到；但它不是维护者资料，不反向链接 `docs/`。
- `tools/` 保存版式引擎、brief、分发脚本与 MCP 服务端。它是交付与接入形式的加速器：几何写死在页型里，内容在 JSON 里。引擎不读 `data/`、不产出判断，因此不改变「卡片划边界、搜索填内容」的边界。
- `tools/mcp_server.py` 把确定性计算暴露成 5 个只读工具（资金带、H2、门类定位、来源分级、检索预算），另有 `resources` 把 `references/`、`data/`、`examples/`、`hosts/` 全量暴露给没有文件系统的宿主。**工具里不含判断**，与版式引擎同一条边界；阈值统一读 `data/params.json`，与文档的一致性由 `skill_check.py` 校验。
- `dist/` 是生成物，**入库**（克隆即可安装，与 `tools/wheels/` 同一取舍），但不手改。它是唯一的安装单元：结构由 `tools/build_skill.py` 决定，内容与源文件逐字节一致，由 `tools/skill_check.py` 校验。
- 每个目录有 `README.md` 作为二级索引，列出本目录职责、文件清单与新增约定；`AGENTS.md` 的入口只列到目录一级，不逐条罗列文件。
- 文件规模按 `AGENTS.md` 的「文件规模与导航约束」控制：Markdown 建议上限 200 行 / 16 KB，硬上限 300 行 / 32 KB，超过 120 行的文件在顶部加「本文导航」。超限先拆再交付，不把新内容追加进大文件。
- 若后续实现加入代码或外部集成，先补充数据边界、接口责任和验证办法，再扩展实现。
