# 验证指南

## 验证目标

确认建议与用户约束一致、事实和假设可区分、步骤可以执行，且交付材料没有夸大确定性或遗漏关键成本。

## 行为闭环检查

| 场景 | 输入要点 | 通过标准 | 样例 |
| --- | --- | --- | --- |
| 只有一个模糊关键词 | 关键词，其他信息缺失 | 先提出少量关键问题，或清楚列出假设后给出有限候选；不伪装成个性化结论 | [01](../examples/01-vague-keyword.md) |
| 零启动资金 | 明确预算为零 | 说明可利用的现有资源、隐性成本和不可省略条件；提供低成本验证步骤与停止指标 | [02](../examples/02-zero-budget.md) |
| 动态市场信息 | 指定地区和行业 | 对关键动态事实提供可追溯来源与日期；无法核实的内容标为待验证 | [03](../examples/03-dynamic-market.md) |
| 用户选定方向 | 方向、周期、资源限制 | 给出客户问题、试验步骤、时间与预算范围、判断指标和下一步行动 | [04](../examples/04-selected-direction.md) |
| PPT/PDF 请求 | 受众、用途、方案内容 | 结构适配受众；数字、假设、来源、日期和结论前后一致；工具不足时提供可复制内容 | [05](../examples/05-deck-request.md) |

## 每次交付前检查

- 是否复述了用户的关键目标和硬约束？
- 是否把事实、估算、假设和待验证事项区分开？
- 是否避免虚构数据、保证结果或把隐性成本写成零？
- 是否包含具体行动、所需资源、预算范围、风险和继续/停止指标？
- 动态信息是否注明来源和日期，或明确标为待核实？
- 是否按用户要求控制了篇幅、语言和交付格式？
- 若生成文件，文件内容是否与审阅过的方案一致？

## 文档与实现变更

当前项目只有 Markdown 规则、框架与行为样例，没有实现代码。本阶段验证聚焦三件事：文件结构与相对链接可用、规则之间不冲突、每个验收场景都有对应样例且样例自检项全部通过。

规则变更后的验证方式是：找到受影响的样例，用新规则重跑一次，逐条对照样例末尾的自检清单；对不上的部分要么改规则，要么改样例，不能两边都不动。

未来引入实现代码后，应按具体行为补充最小验证，不以一次宽泛测试替代行为闭环验证。
