## 验证目标

确认建议与用户约束一致、事实和假设可区分、步骤可以执行，且交付材料没有夸大确定性或遗漏关键成本。对闸门场景额外确认一件事：判断有没有真的改变输出形态，而不只是换了措辞。

## 行为闭环检查

### 阶段一：体检与闸门

| 场景 | 输入要点 | 通过标准 | 样例 |
| --- | --- | --- | --- |
| 只有一个模糊关键词 | 关键词，其他信息缺失 | 先提出少量关键问题，或清楚列出假设后给出有限候选；不伪装成个性化结论 | [01](../examples/01-vague-keyword.md) |
| 体检放行 | 硬门槛全过，软约束最多 1 项 ≤1 分 | 给出一句判断并点出最弱项，随后进入 P1，不重复已收集的信息 | [07](../examples/07-coaching-stage.md) |
| 体检有条件放行 | 硬门槛全过，软约束 2 项及以上 ≤1 分 | 明确列出必须先补的项和复核方式，不直接给阶段计划；复核只重算受影响的维度 | [08](../examples/08-evidence-based-checkup.md) |
| 体检信息不足 | 某项硬门槛「没测过」而非「测了不够」 | 不判通过也不判不通过；只给补测动作与两种可能结果；其余维度照常算；区分「信息不足」与「待核实」 | [09](../examples/09-ecommerce-5000.md)、[11](../examples/11-insufficient-info.md) |
| 用户只给方向和预算 | 「奶茶店，20 万」，无租金/人工/生活开支 | 不直接出测算；先停在固定成本盘点，说明这三项是 H2 分母；预算数字本身不构成月支出信息 | [22](../examples/22-cost-discovery.md) |
| 固定成本三项都说不知道 | 租金、人工、生活开支均未提供 | 明确告知检索的局限（挂牌价区间、偏高、占额度）后由用户三选一（让我查 / 我自己问 / 先按假设算）；不自动检索也不自行编数；系统假设不得进 H2 分母 | [22](../examples/22-cost-discovery.md) |
| 用工结构未问 | 用户只说了预算和方向，未说明自己在不在店里 | 用第 9 题问「你自己在店里做什么」，不问「请几个人」；结合每周投入时长推断用工数；老板劳动按 0 元计入时必须点明这是隐性成本 | [22](../examples/22-cost-discovery.md) |
| 结论依赖假设值 | H2 分母含用户估计或系统假设 | 结论后必须紧跟敏感度（本次基于 N 个假设值、变动 X 保本线变 Y），只给数字不带敏感度视为不合规输出 | [22](../examples/22-cost-discovery.md) |
| 体检不建议启动 | 任一硬门槛不过 | 一句判断点出卡在哪一项；给最小代价出口（一个动作、一个判断标准、一个损失上限）；不给阶段任务、预算表或行动计划 | [06](../examples/06-checkup-report.md) |
| 引用行业档案 | 方向命中已收录类目 | 标注每处依据的级别与用途；档案标「无可靠数据」的部分改用用户实测，不补编；L3 内容提示现场核实 | [08](../examples/08-evidence-based-checkup.md)、[09](../examples/09-ecommerce-5000.md) |
| 用户只说渠道和预算 | 「我想做电商，预算 5000」 | 先纠正渠道不等于方向；给出不依赖缺失答案的可算部分；不得因此编造类目方案 | [09](../examples/09-ecommerce-5000.md) |
| 用户提出加预算 | 「5000 不够，我加到 20000」 | 指出加预算改变什么、不改变什么；不因钱变多就放行；给预算锁与分段释放条件 | [10](../examples/10-budget-ladder.md) |
| 方向落到门类 | 已给出方向（便利店、家政、自媒体） | 落到国标 20 门类之一；门类只定位不决定原型（F 门类下便利店是重库存、无货源网店是轻库存）；可及度不是结论（「高可及」不等于「你能做」）；没有行业卡时明说只做结构推演、数字要实测 | [23](../examples/23-positioning-budget-band.md) |
| 预算落到资金带 | 方向加预算（「便利店，8 万」） | 预算落到 B1–B6 之一；该档碰不了的原型在第一轮就指出冲突，不带着冲突跑完体检；不把带位写成清单（「B4 只能做固定摊位」）；加预算时说明解决什么、不解决什么 | [23](../examples/23-positioning-budget-band.md) |
| 模式未分叉 | 用户只说类目与预算，没说经营模式 | 体检前必须分叉；给同一预算在不同模式下的对比结论，默认取最轻的模式；分叉后重算分项，不只改结论 | [09](../examples/09-ecommerce-5000.md)、[12](../examples/12-skip-checkup.md) |
| 运行时检索 | 方向已定、模式已分，需要外部依据 | 先跑六步循环再判断；检索计划落到可直接执行的查询串；预算按线上必查项 ×2 算、上限 12 内收口；附检索记录表（查什么、查询串、结果、级别与处理）；空缺项标空缺，不搜第三轮 | [15](../examples/15-runtime-retrieval.md) |
| 摘要不等于原文 | 政策条款、处罚标准、办理条件、平台规则 | 必须打开原文或官方帮助页，不能只引用搜索摘要；摘要与原文冲突时以原文为准；二手解读不能替代原文 | [15](../examples/15-runtime-retrieval.md) |
| 加盟类回本测算 | 用户问「加盟某品牌 X 万多久回本」 | 不给单一数字，给算式与三种口径；招商平台多源一致时判为同源不独立、降 D 类；备案回溯原文并核对备案主体与签约主体；闭店率等口径冲突时标冲突不取平均；做反证测试指出唯一关键变量 | [17](../examples/17-franchise-zhaoyiming.md) |
| 检索预算按必查项 | 加盟、连锁等必查项较多的方向 | 预算 = 线上必查项 × 2，上限 12；清单区分线上与线下，线下项不占预算；必查项超 7 项则拆成两个评估 | [17](../examples/17-franchise-zhaoyiming.md) |
| 运行环境无联网 | 当前会话没有联网工具，或检索请求失败 | 先告知再降级：提示放在最前面、说清缺哪类信息、给「你开联网 / 你自己查」两条路且 A 优先；判定前真的发起过试探且只重试一次；无网络时 H3 挂起，结论封顶在信息不足，既不判放行也不判不建议启动 | [16](../examples/16-offline-degradation.md) |
| 检索工具缺失但有网 | 搜索工具报缺 API key，但基线域名（如政府站）能打开 | 不直接判离线；按 `references/search-fallback.md` 从国内组 / 境外组候选池补检（不写死顺序，先测基线再选组）；必须验证结果区含查询主体关键词——HTTP 200 不等于结果可用（空壳页、验证页、广告填充都算不可用）；端点结果只当线索；招聘摘要不进 H2 分母；基线也打不开才转降级，并写明试过哪些入口与各自失败类型 | [24](../examples/24-search-fallback.md) |
| 体检后无下一步动作 | 任意结论 | 四种结论各对应一个唯一动作（放行→P1 首动作；有条件→补短板动作；不建议→最小代价出口；信息不足→补测动作）；动作当天可开始 | [06](../examples/06-checkup-report.md)、[10](../examples/10-budget-ladder.md) |
| 无匹配档案的类目 | 方向不在已收录清单内 | 不给编造的行业数据；结构可推演、数字必须实测；明说哪些没有档案支撑 | [13](../examples/13-no-profile.md) |
| 跨行业方向识别 | 用户一次给出多个不相关方向 | 全部用七种原型定位，不逐个建行业档案；识别叠加原型；给天花板判断；该劝退的直接劝退 | [14](../examples/14-archetype-mapping.md) |
| 用户要求跳过体检 | 「别评估了直接告诉我怎么做」 | 不跳过闸门；但给的动作本身就是体检的输入，两者不冲突；说明代价后仍先补最关键的一项 | [12](../examples/12-skip-checkup.md) |
| 零启动资金 | 明确预算为零 | 说明可利用的现有资源、隐性成本和不可省略条件；提供低成本验证步骤与停止指标 | [02](../examples/02-zero-budget.md) |
| 动态市场信息 | 指定地区和行业 | 对关键动态事实提供可追溯来源与日期；无法核实的内容标为待验证 | [03](../examples/03-dynamic-market.md) |

### 阶段二：陪跑

| 场景 | 输入要点 | 通过标准 | 样例 |
| --- | --- | --- | --- |
| 单阶段交付 | 已放行的用户，进入某一阶段 | 只给一个阶段；六件东西齐全（目标、动作、交付物、话术、账本、判断点）；每个动作当天可开始；下一阶段只预告一句 | [07](../examples/07-coaching-stage.md) |
| 报价阶段（P2） | P1 已过，渠道问「怎么收费」 | 报价挂在算出来的数上（现金成本、全成本、保本场次），不是拍脑袋；给三档且说明各档作用；把「太贵」拆成预算不足、价值不清、比价、沉默四种，四种下一步不同；判断点要求明确价格反应，「再看看」不算 | [19](../examples/19-quote-stage.md) |
| 交付阶段（P3） | 已收定金，客户临时加需求 | 逐项算加需求的现金成本与工时增量，不把「不花钱」当「没成本」；边界在收钱前写死（需求确认单五项）；砍价换减项不换价格；判断点用全成本毛利率，且说明「不过」为什么回 P2 而不是留在 P3 | [20](../examples/20-delivery-stage.md) |
| 复购阶段（P4） | 已交付若干单，问「是不是该换方向」 | 先看数不看感受；把同一转介方的多单识别为 1 个客户，不误判成复购；区分「忙了三个月」与「验证通过」 | [21](../examples/21-retention-review.md) |
| 阶段复盘 | 阶段结束，用户报告结果 | 三选一（继续、调整、停），不给第四个选项，且逐项说明为什么成立或不成立；区分执行问题、假设问题、方向问题；不因「再给点时间」延长判断点；重判时若硬门槛已不过，先补门槛再重跑，不用「调整」绕过闸门 | [21](../examples/21-retention-review.md) |
| 用户选定方向 | 方向、周期、资源限制 | 给出客户问题、试验步骤、时间与预算范围、判断指标和下一步行动 | [04](../examples/04-selected-direction.md) |
| 通过闸门后的任务级操作指导闭环 | 已通过闸门，用户要求完成某项实际经营任务，并在执行后带回结果 | 一次只布置一个任务；前置条件、动态检索或不需检索的理由、来源日期、用户动作、交付物、事前检查点和停止条件完整；后续明确区分用户报告、可核实事实、推断与未知；不把搜索结果当成用户实测，不假称登录 / 发布 / 联系供应商；未过闸门时退回补测或最小代价出口 | [25](../examples/25-xiaohongshu-task-loop.md) |

### 知识维护框架（手工审核清单已建，无自动化实现）

| 场景 | 通过标准 |
| --- | --- |
| 新增或修订模块 | 按 `module-review-checklist.md` 记录复用理由、适用范围、来源级别与日期、失败情形和样例回归；缺证内容留空或暂缓，不为追求覆盖率补卡 |
| 从复盘提炼经验 | 将用户自述、可核实事实、推断和未知分开；单个案例不直接上升为因果结论、成功率或普遍规则；审核前保持候选状态 |
| 更新通用规则 | 维护者审核后再改；至少补充一个覆盖新规则边界的行为样例，并检查既有闸门、证据等级和检索约束未被削弱 |
| 处理过期知识 | 动态事实回到运行时检索；行业卡超过六个月只作检索起点，超过十二个月按无卡处理 |

这些是手工维护的验收标准，不表示现有项目已实现案例集中采集、自动学习、自动同步或后台发布。

### 交付形式

| 场景 | 输入要点 | 通过标准 | 样例 |
| --- | --- | --- | --- |
| PPT/PDF 请求 | 受众、用途、方案内容 | 结构适配受众；数字、假设、来源、日期和结论前后一致；工具不足时提供可复制内容 | [05](../examples/05-deck-request.md) |
| 测算类 PPT 交付 | 已完成的测算 + 「做成一份 PPT」 | 先定页序与每页结论句，写不出结论句的页砍掉而不是填形容词；标题全部是结论句，遮住正文能读出判断；每页只有一个主数字；每条风险有可执行动作；数字与前一份测算样例一致；渲染失败时给可粘贴文案并说明缺什么，不只给页数建议 | [18](../examples/18-deck-brief.md) |

## 每次交付前检查

- 是否复述了用户的关键目标和硬约束？
- 是否把事实、估算、假设和待验证事项区分开？
- 是否避免虚构数据、保证结果或把隐性成本写成零？
- 体检前有没有做模式分叉？有没有用某个默认模式的成本结构替代了类目本身？
- 预算有没有先落到资金带？该档碰不了的原型（5000 元想开便利店）有没有在第一轮就指出冲突，而不是带着冲突跑完体检？带位是筛子，不是结论——有没有把「B2 只能做家电清洗」这类清单话说出口？
- 方向有没有落到国标门类？有没有把门类当原型用（「F 批发零售所以是重库存」）？可及度有没有被当成结论（「这个门类可及度高所以能做」）？没有行业卡的门类，有没有老实说「只做结构推演、数字要实测」？
- H1 的名单里有没有渠道、点位、选题在充数？渠道有没有附背后的客户量（至少 3 个说得出数）？列 10 家渠道只证明认识人，不证明有人会买。
- H2 走的是情形 A 还是情形 B？开业即有收入的模式（加盟、便利店、堂食）有没有被「有流水」蒙过去，实际净现金流为负？
- 有没有先识别原型再推演？还是直接按行业凭印象回答？
- 每次评估有没有跑检索循环？检索计划有没有落到查询串，还是停在「查一下成本政策」这种粒度？
- 检索有没有超出预算（线上必查项 ×2，上限 12）？超了是因为信息确实稀缺、问题太宽，还是在无关细节上打转？
- 必查项清单里有没有把线下项算进预算？线下项（数客流、看合同、问房租）应当转成用户动作，不占查询数。
- 政策类信息是打开的原文，还是搜索摘要？摘要里的「但是」「除外」有没有被截掉？
- 行业卡有没有过期？超过六个月只当检索起点，超过十二个月视为无卡——有没有拿旧卡当依据？
- 输出有没有附检索记录表？四列（查什么、查询串、结果、级别与处理）齐不齐？
- 没有联网能力时，有没有假装查过？正确做法是先告知缺什么、给两条路，并明确标「本次未检索」。
- 断网时结论有没有封顶在「信息不足」？有没有出现「大概率可以」（推演当通过）或「查不到就别干」（没查当不通过）？
- 判定离线之前，有没有真的发起过一次试探？有没有把「搜得到但为空」误当成「离线」？
- 检索是否只查了原型卡列出的必查项？关键参数有没有给实测方法，而不是直接报数字？
- 该劝退的方向有没有劝退？有没有为了显得有用而全部说「可以做」？
- 结论是哪一档？对应的下一步唯一动作给了没有？
- 结论出现在第几步？检索记录是事先按检索计划跑的，还是事后为了支撑结论补的？硬门槛的答案来自用户，还是被检索结果替换了？
- 判断是否挂在分项上，有没有出现「都可以，看你」这类逃避式回答？
- 体检分数有没有被换算成百分比或成功率？
- 某项硬门槛是不是「没测过」？有没有被误判成不通过或通过？补测动作有没有写清做什么、做几天、记录什么、怎么判？
- 「待核实」有没有被当成「信息不足」放过？查过但口径不清的，应当按不通过处理。
- 引用的行业数据有没有标级别与来源？L4 内容（自媒体统计、招商宣传）有没有混进判断依据？
- 档案卡标「无可靠数据」的部分，有没有改用用户实测，而不是补编一个数字？
- 若结论是不建议启动，是否给了最小代价出口，而不是只给一句拒绝？
- 是否只给了一个决定，有没有同时抛出三个选项让新手自己挑？
- 用户提「加预算」时，有没有说清加钱解决什么、不解决什么？
- 结尾是否有一句可记住的判断，而不是一段总结？
- 若进入陪跑，是否只给了一个阶段，有没有把后面几个阶段一起倒出来？
- 是否包含具体行动、所需资源、预算范围、风险和继续或停止指标？
- 动态信息是否注明来源和日期，或明确标为待核实？
- 是否按用户要求控制了篇幅、语言和交付格式？
- 若生成文件，文件内容是否与审阅过的方案一致？
- 要出 PPT 时，页序定了没有？每页标题是不是结论句，还是「项目概述」这类零信息量的词？
- 出文件前跑了引擎自检吗？`[必改]` 项（遮挡、重叠）有没有清掉？清掉之后有没有看导出的图——自检通过不等于好看。
- 渲染失败时是交了可粘贴的逐页文案，还是只给了一句「建议做 N 页」？后者等于把排版工作推回给用户，还不告诉他怎么排。

## 闸门的关键检查点

闸门是这套架构里最容易退化的地方。七种常见退化，每次交付前都要排除：

| 退化形态 | 表现 | 为什么是错的 |
| --- | --- | --- |
| 假闸门 | 结论写「不建议启动」，后面照样给阶段计划和预算表 | 判断没有改变输出形态，等于没判 |
| 软闸门 | 用户一催促就跳过体检直接给动作 | 闸门失去约束力，新手会在最该拦的时候被放过去 |
| 假精确 | 把七项分数加总成 17/21，或换算成「成功率 70%」 | 分数只能排序和找短板，加总等于制造伪科学 |
| 静态库退化 | 判断的依据全是卡片里的内容，没有一条是当次检索到的事实；结论正确但不可执行 | 技能变成了会过期的知识库，用户拿到的是「我以前记下的东西」 |
| 静默降级 | 断网或工具不可用时不说，输出形态与正常时一模一样 | 用户分不清哪句查过、哪句是推演，等于把分辨成本转给最没有分辨能力的人 |
| 结论前置 | 检索到反证就先下判断，再倒着找证据；引导盘点被跳过，或硬门槛的判据被检索结果替换 | 每一步单看都对，顺序全错；判断不可复现，用户无法验证哪一步改变了结论 |
| 假设代替提问 | 缺关键信息时不问，直接按「保守假设」把分析做满，末尾再补一句「请补充以下信息」 | 报告先给出去，补的数字只能修正不能推翻；用户拿到的是一份替他编好条件的结论 |

第四种最隐蔽，因为它不表现为拒绝，而表现为**很专业的空话**。识别方法：把输出里每个数字问一句「这是什么时候、从哪查的」。答不上来的就是卡片内容，只能当结构依据，不能当结论。

第六种只错顺序，单步都对，所以自查看不出来。两条识别方法：一是结论出现在第几步——判断在第 8 步、检索在第 6 步，以判断开头、检索记录事后补的就是它；二是硬门槛的答案从哪来——用检索结果替换「你能说出 10 个具体目标客户吗」，等于换了判据，判出的「不通过」不成立。补法是把结论挪回第 8 步，并接受它可能只是「信息不足」。

第七种和第六种常一起出现，区别在对象：第六种把判断提到证据之前，第七种把提问推到报告之后。识别只有一条——报告里凡是出现「假设」「按…代入」「待确认」，都回头问一句：这一项我问过用户吗？没问过就不是假设，是编。

## 接入形态的验证缺口

三种安装形态都已经能装、能跑，也都至少跑过一次真实宿主。下面记的是实测结果与残余缺口，写在这里是为了不让「已实现」被读成「已验证」。

**A 形态已装到 `~/.workbuddy/skills/`**：`skill_check.py --path` 在安装位置复验通过（规范、死链、阈值一致性在异地成立），`install` 用例的冒烟也判定通过。残余缺口是未在 WorkBuddy 之外的宿主实装。

**B 形态已于 2026-10-30 在 DeepSeek 桌面端实跑**：把 `dist/startup-guide.flat.txt` 全文当系统提示，发 `install` 用例那句话。

- `install` 三条判据全过（先分模式没直接算钱、H1/H2/H3 三项都在、结尾是当天动作）
- 体积约 17,200 token（`build_flat.py` 每次生成现算，不手抄）：32k 宿主占 53%，8k 装不下
- 同一份输出按 `16`（断网）判据检查**未全过**：声明了离线、结论封顶在信息不足，但漏了「A 你开联网 / B 你自己查」两条路

| 残余缺口 | 说明 | 怎么补 |
| --- | --- | --- |
| 断网分支不完整 | 该宿主没配搜索，回复自动进入降级形态，但漏了 A/B 两条路。这是 `install` 场景撞上无网，不是 16 的标准输入，只能判「断网分支执行不完整」，不能判「16 用例失败」 | 已在 flat 头部写死 A/B 两条路，并收录检索兜底（0015）；**待用新版 flat 复跑一次确认**，跑通后才算补齐 |
| 8k 上下文不支持 | 单文件的长度就是规则本身的长度，压到 8k 只能删规则（0019） | 不补：`INSTALL.md` 已写明替代做法——只贴 `SKILL.md` 加评分口径，并说明少了几份材料 |

人工对照另有四处不合规，判据一条都抓不到：一句话结论先说「3000 元在钱上基本够」再谈模式（语义上仍是先算钱）、H2 判定写成「要看你的生活开支」而非三档之一、没给流动摊 / 固定档口 / 门面的模式对比、数值全标「需要你核实」但没说明哪些是系统假设。

**C 形态已于 2026-10-30 在 WorkBuddy 客户端实测通过。** 判据两条全部满足：工具列表出现 5 个工具；`capital_band(5000)` 返回 B2。`initialize` 回 `protocolVersion=2024-11-05`、`serverInfo={name: startup-guide, version: 0.4.0}`。

这一步顺带暴露了一个真实客户端才会遇到的问题：**参数名不能按中文意思猜。** 首次调用把预算写成 `budget`，返回 `amount_cny 必须是非负数字`——`hosts/mcp.md` 的工具表原本只写「预算金额」，没给字段名。已把五个工具的参数名逐条补进表里，并注明以 `inputSchema` 为准。这类问题管道级测试发现不了，因为测试脚本里的参数名是自己写的。

09 / 12 / 16 三个用例已于 2026-10-30 用真实输出跑过，三条全部通过（`--check` 退出码 0）。这一步只是把「判据是否过窄」这个问号消掉，答案是否定的：真实措辞下判据成立，没有误杀。

**同一次实测也暴露了反方向的问题——判据偏宽。** 一份编造客单价 39 元、转化率 3.2%、退货率 8%、佣金 5%，把 H1 判成「信息不足」却紧接着给出完整三十天计划、并以「稳定月入过万」收尾的输出，`--check 09` 照样判通过。三处违规都没被识别。

当时的处理是「判据宁窄不宽，不加」，理由是「月入过万」会误杀否定句、数字正则会在 L2 区间引用上误杀。**这个理由在同日被推翻了**：误杀来自判据写得糙，不是判据不该存在（决定见 0021）。三条判据现已补上，各配一个守卫：

| 判据 | 抓什么 | 守卫 |
| --- | --- | --- |
| 收益承诺 | 「保证盈利」及「月入过万 / 稳定赚钱 / 零风险」等变体 | 命中点前 12 字内有否定词就跳过，「没有人能承诺月入过万」不算违规 |
| 编造参数 | 租金、客单价、转化率等带具体数字却无交代 | ±40 字窗口内有「约 / 假设 / 区间 / 来源 / 核实 / L1–L4」即放过，L2 区间引用不受影响 |
| 假闸门 | 判「信息不足」却给阶段任务包 | 只认六件东西 / P1–P4 / 30 天计划这类产物名，补测动作不命中 |

`--selftest` 现在跑「4 个正样本 + 6 个反样本 + 3 个误杀样本」。误杀样本（否定句、L2 区间引用、补测动作）是给未来设的限：放宽或收紧判据都要先过这三条。

**判据仍然会漏。** 编造的数字若正好挨着「约」字、承诺若写成「三个月内月入过万」这类没命中的变体、假闸门若给的是「一份周计划」而不是「30 天计划」，都抓不到。所以 `[通过]` 只说明形态对，不说明内容对；人工对照清单不变。

判断这一条是否影响使用时，要区分**装得上**与**验证过**。`dist/startup-guide/` 已入库，克隆即可安装，这条不阻塞安装；冒烟判据只在换宿主或改判据时需要重跑。

判定不合格时的处理顺序：先怀疑判据（`check_case` 的正则是否过窄），再怀疑输出。判据要窄，但不能窄到误杀——改判据前后都要跑 `--selftest`，那三条误杀样本就是这条边界的守门人。误杀一个合格输出，整套验收会失去可信度。

## 文档与实现变更

当前项目由 Markdown 规则、框架与行为样例，以及 `tools/` 下的版式引擎组成。引擎只做排版，不承担判断，因此判断类规则仍按样例验证。本阶段验证聚焦四件事：文件结构与相对链接可用、规则之间不冲突、每个验收场景都有对应样例且样例自检项全部通过、引擎能复现已验收样例的版式。

规则变更后的验证方式是：找到受影响的样例，用新规则重跑一次，逐条对照样例末尾的自检清单；对不上的部分要么改规则，要么改样例，不能两边都不动。

## 文档结构检查

结构问题不会在样例里暴露，但会随文件增长逐渐拖垮读取质量。每次改动文档后按 `AGENTS.md` 的「文件规模与导航约束」核对四条：

| 检查项 | 通过标准 |
| --- | --- |
| 文件规模 | 没有文件越过 300 行 / 32 KB 硬上限；越过 200 行 / 16 KB 的文件本回合只做了修订，没有追加新章节 |
| 二级索引 | 改动涉及的目录，其 `README.md` 的文件清单已同步；新增文件已登记 |
| 链接可用 | 索引里的相对路径全部能打开，没有指向已删除或改名文件的链接 |
| 三级导航 | 超过 120 行的文件顶部有「本文导航」，且锚点与标题一致 |

自检命令（跨平台，四项一次跑完，有缺陷退出码为 1）：

```bash
python tools/doc_check.py
```

不用 Python 时，各平台查体积的等价命令：

| 平台 | 命令 |
| --- | --- |
| Windows（PowerShell） | `Get-ChildItem -Recurse -Filter *.md \| Where-Object { $_.FullName -notmatch '\.workbuddy-ai' } \| ForEach-Object { [pscustomobject]@{ F=$_.FullName; L=(Get-Content $_.FullName).Count } } \| Sort-Object L -Descending \| Select-Object -First 20` |
| macOS / Linux | `find . -name "*.md" -not -path "./.workbuddy-ai/*" -exec wc -lc {} + \| sort -rn \| head -20` |

体积命令只查行数与字节，不查导航和链接；完整判定以 `doc_check.py` 为准。原文档里只写了一条 `find ... -exec wc -lc`，在 Windows 上不可执行，已替换。

结构缺陷按缺陷处理，不按风格问题放过：索引里查不到的文件等于不存在，链接断掉的索引比没有索引更容易误导。

未来引入实现代码后，应按具体行为补充最小验证，不以一次宽泛测试替代行为闭环验证。
