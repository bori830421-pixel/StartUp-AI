# 样例 16：运行环境没有联网

覆盖能力：离线降级、运行时检索、启动条件体检
对应验收场景：`docs/verification-guide.md`「运行环境无联网」

本技能的第 3 步依赖联网。没有网络时，最容易犯的错不是「答不出」，而是**答得跟平时一模一样**——把卡片内容当检索结果说出去，用户以为已经核实过。

本例演示正确形态：先判定、先告知、给两条路；H3 挂起但仍给当前投入立场，不把断网扩展成整份评估没有结论。

## 输入

> 我想在小区门口摆个早餐车卖包子豆浆，预算 3 万，一个人干。**（当前会话无联网能力）**

## 一、先判定，不要凭感觉

不要一上来就说「我搜不了」。先拿检索计划的第 1 条试一次：

```text
查询串：<城市> 早餐车 摆摊 管理规定 食品摊贩 备案
结果：工具调用失败（连接超时）
```

换一条更宽的查询串再试一次：

```text
查询串：食品摊贩 备案 办理 条件
结果：失败
```

两次都失败 → 判定离线。**到此为止，不再试第三条。** 继续试是把预算浪费在证明自己没网上。

## 二、先告知，不要先降级

输出第一段就是提示，不能藏在结尾：

> 这个判断需要联网查当前的政策和价格，我这边现在**连不上网**。
>
> 缺的是这两类信息：① 早餐车在你们那儿要不要备案、要什么材料（政策原文）② 当地早餐的实际售价与一个早上的销量。
>
> 两条路，你选一条：
> **A 你开一下联网，或换个能联网的环境**，我重跑一遍检索，3–5 分钟给你完整判断。
> **B 我把结构判断和要查的清单给你**，你去查，把结果发我，我接着判。
>
> 先说结论：**现在不能给启动放行**；但可以判断当前是否该买车或付点位费，并把现有资金与时间约束算完。

四条都做到位了：放在最前面、说清缺哪类信息、给两条路且 A 优先、不给第三个选项。

**不要写「我先大致帮你分析一下」。** 这句话一出口，后面所有内容都会被当成有依据的判断。

## 三、用户选 B：无网络下能算什么

用户回：「B，我今天就去问。」

先算不需要网的部分，别让他空等：

| 维度 | 能不能算 | 结果 |
| --- | --- | --- |
| H1 客户可达 | **能**（用户侧数据） | 信息不足。说不清「谁会买」，只能说「小区人多」 |
| H2 现金流断点 | **能** | 按样例假设展示：3 万减车与设备约 1.2 万，剩 1.8 万；月固定支出暂按 4,000 元情景，可撑 4.5 个月；早餐首月有现金收入，但净流出和爬坡仍须核验，不能凭该情景判 H2 通过 |
| H3 合规前置 | **不能** | 信息不足。食品摊贩备案、点位许可都是政策事实，推演不算 |
| S1 资金匹配 | 能 | 2 分。启动 1.2 万对 3 万，覆盖 2.5 倍，但没算首批原料与周转 |
| S2 时间匹配 | 能 | 2 分。一人干早餐，凌晨 3 点到上午 10 点，7 小时；但连续做需要下午补觉，实际是半个全职 |
| S3 能力缺口 | 部分 | 待核实。「需要什么资质」是外部事实，无网查不了，该项先标待核实 |
| S4 失败可逆性 | 能 | 2 分。餐车与设备可转卖，折价约三到五成；原料有保质期，退出时是损耗 |

**启动状态：暂不放行；当前投入立场：先不买车、不付点位费。** 这是在保护 3 万元且亏损会影响基本生活时的临时建议，不是把方向判死。

H3 因无网络而挂起；H1 的点位需求也没有实测。现有的现金、用工和时间结构仍可计算。早餐车是否允许经营不能靠推演当通过；同样，没查也不能当成已失败。

## 四、检索清单怎么给

四到六条，每条带判据和「带回什么算数」：

| # | 查什么 | 去哪查 | 带回什么算数 |
| --- | --- | --- | --- |
| 1 | 早餐车要不要备案 | 区市场监管局办事窗口，或当地政府网搜「食品摊贩 备案」 | 办事指南链接、受理单、或窗口给的书面材料清单 |
| 2 | 小区门口能不能摆 | 小区物业 + 属地城管 | 物业的书面同意；城管的口头答复只能算线索 |
| 3 | 健康证 | 社区卫生服务中心或疾控 | 办理点、费用、周期 |
| 4 | 当地早餐售价 | 早上 6:30 去 3 家早餐摊，各买一份 | 实际价格、排队人数、出摊时间 |
| 5 | 一个早上能卖多少 | 在上述 3 家各站 30 分钟，数出餐份数 | 三个数字，不用平均数，取最低 |

第 4、5 条不需要网，今天早上就能做完。**离线不等于什么都做不了**，这句话要说给用户听，否则他会以为今天白问了。

然后说清什么样的结果算数：

- 办事指南链接、受理单 → 按 L3 使用，我把 H3 转成通过
- 「我问了窗口，他说可以」→ 记为**用户口述**，H3 从「信息不足」推进到「待核实」，仍不算通过
- 「物业说应该行」→ 同上，且物业不是主管部门，只能当线索
- 「我朋友说不用办」→ 不算查询，维持信息不足

「待核实」按不通过处理，但给出口：补一张办事指南截图或受理单，就能转成通过。

## 五、结论与下一步

> **现在先不买车或付点位费。3 万是否够用可以先按设备、月支出和生活费算；能不能在该地点经营、要不要备案仍待官方核实。**

下一步唯一动作，拆成今天和明天两件：

1. **今天早上 6:30**：去 3 家早餐摊各买一份，记价格；再各站 30 分钟数出餐份数
2. **明天上午**：跑一趟区市场监管局窗口，问一句「小区门口摆早餐车要不要备案、要什么材料」，把办事指南拍下来

**判断标准**：

- 3 家平均一个早上 80 份以上 + 窗口明确说要备案且能办 → H1 和 H3 同时有着落，可以进 P1
- 窗口说要备案但周期超过 1 个月 → 准备期不够，先算清这一个月怎么撑
- 物业明确不同意 → 换点位，不要在同一个门口反复试

## 六、三种错误做法

| 错误做法 | 后果 |
| --- | --- |
| 把卡片内容写成「按目前政策，食品摊贩需要备案」 | 用户以为已核实。万一他所在城市已取消备案，他白跑一趟；万一更严，他没准备 |
| 因为没网就判「不建议启动」 | 误杀。H1 和 H3 只是没测，不是测了不够 |
| 跳过 H3，说「小生意一般不用管」 | 软闸门的离线版本。早餐是食品，出问题直接扣货罚款 |

三种的共同点是**没把「没查」当成一个独立状态**。它是信息不足，不是通过，也不是不通过。

- [x] 提示放在输出最前面，说清缺的是政策原文与当地价格两类
- [x] 给了 A / B 两条路，A 优先，没有抛回「要不要继续」
- [x] 无网络下照常算了 H1、H2 与 S1–S4，没有让用户空等
- [x] H3 挂起且不给启动放行，但仍给当前投资立场，没有把方向判死
- [x] 检索清单每条带判据与「带回什么算数」
- [x] 说清了用户口述与官方原文的区别，并给了补凭证的出口
